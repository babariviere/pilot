# Source-matched Day package inputs

`apps/desktop/scripts/day_build_inputs.py` builds inputs for the existing
`bundle_runtime` assembler. It does not sign, notarize, archive, release,
install, register or start an app or service. The shipping desktop selection
and legacy apps are unchanged.

## Recipe

The input is a full immutable Pilot commit, not a working tree or bookmark.
The builder extracts Git objects into a fresh private directory, then:

1. Checks the native macOS arm64 host, installed Rust/Cargo 1.99.1,
   mise-managed mbx and official Longbridge NSH 0.5.0. The installed CLI checksum
   is pinned. Day's lock must select only release f4d68f7 NSH crates and
   must not contain GPUI. There is no CLI-build or source-patch fallback.
2. Builds Day's own `pilot-desktop`, with `macos-host`, and the existing
   `pilot-desktop-update-helper`, with `native-macos`. Cargo JSON identifies
   each actual output. It also builds `pilot-artifact-host` with `artifact-host`
   and checks its compiled source/recipe identity through the existing transport.
   There is no renamed stock runner.
3. Builds the required existing `pilot-visual-worker` in an isolated
   workspace, using its unchanged sources/dependency versions and the
   Day's `apps/day/visual-worker.Cargo.lock` as a seed. Adding `[workspace]` isolates it from GPUI;
   Cargo prunes the seed offline, and every resolved package version/source/
   checksum must be present in that seed. Builds then use `--locked`.
   The resulting manifest and lock digests are recorded. The pinned QuickJS-NG
   0.17.0 archive is supplied separately and checksum-checked by the
   existing extractor. This builder never downloads it.
4. Runs the installed CLI's **build**, not package/run, for `Connected.tsx`.
   A snapshot-only `nsh.json` uses the fixed app ID and exact `Bridge::METHODS`
   host grant. The development config is not edited. The guarded Day
   launcher seeds the genuine released runner lock. No package-manager
   lifecycle hooks or automatic package-manager switching run.
5. Copies the complete generated bytecode, JS/maps, capabilities, app ID
   and assets to `nsh/`. Unexpected files, links, dynamic chunks, widened
   capabilities, missing files and changed copies are refused. The bootstrap
   disables runtime-delivered chunks. `gui-resources.json` binds the full
   inventory to the executable digest, immutable source, target and release.

This full-distribution recipe remains the default, including in CI. The
[connected development candidate](day-connected-candidate.md) explicitly selects
only its consumed main executable and NSH resources in the same builder. It has
a distinct receipt kind, no helper/visual evidence and no QuickJS archive input.
Both selections use the same source-matched recipe hash and shared local caches;
no separate target/store or candidate-specific builder is added.

Cargo is offline and runs through the current Day MBX dispatcher. The builder
keeps the real HOME so global MBX settings and shared caches apply. It does not
set Cargo cache/target paths, job counts, debug or incremental settings.
Ambient trust, provider/discovery credentials, compiler wrappers, Cargo tuning,
NSH resource overrides and package-manager configuration are not inherited.
Missing dependencies fail, rather than bootstrapping or repairing shared state.

## Receipts and trust

Both app and helper expose only the exact single diagnostic argument
`--build-input-receipt`. It exits before startup, AppKit, service or update
work. The linked updater dependency reports its compiled source, recipe,
target, profile, compiler identity and updater configuration. The builder
compares both reports with the actual build selections and rejects any
difference. Binary hashes, genuine Cargo artifact messages, tool hashes,
connected config and the isolated worker manifest digest are also kept.

The default lane deliberately compiles **unconfigured** trust. Its receipts
say `development-rust-inputs`, and `installable_update` is false. The existing
bootstrap still refuses missing compiled trust. A diagnostic report is not
a signature, `ExpectedTarget`, READY/COMMIT, startup acknowledgement or proof
that a package is installed.

`--production` requires the existing explicit public updater configuration
and approved distribution-policy setting through Day's `configuration` adapter
in `day_build_inputs.py`, which uses the unchanged `gui_release.configuration`
validation.
It builds the optimized release profile and compares the actual compiled
configuration in both binaries. It neither creates a key nor accepts test
keys as production evidence. Even configured inputs say
`installable_update: false`: a signed payload and its independent manifest
are still required. Missing production configuration/payload is unavailable,
not a successful update.

## Entry points

Prepare dependencies/tools separately. The builder never bootstraps them.
Use absolute qualified tool paths, global MBX defaults and a fresh output:

```sh
export NSH_DAY_CLI=/absolute/installed/longbridge/nsh
export NSH_DAY_MBX="$(mise which mbx)"
export NSH_DAY_REAL_CARGO=/absolute/installed/toolchain/bin/cargo
export RUSTC=/absolute/installed/toolchain/bin/rustc
export PILOT_DAY_QUICKJS_ARCHIVE=/private/build/quickjs-ng-0.17.0.tar.gz
python3 apps/desktop/scripts/bundle_runtime.py rust --gui day \
  --source FULL_COMMIT --output /private/build/day-inputs
```

The same implementation is available directly through `day_build_inputs.py`.
The legacy `rust` default stays GPUI. `assemble(..., gui_resources=inputs / "nsh")`
(CLI: `bundle --gui-resources`) consumes these files in the unchanged trusted
fixed app/helper layout. Assembly signs its output, so it is a **separately
authorized** action, not part of input verification here. App/helper trust
equality, visual-worker, runtime/native-helper receipts, NativePlatform,
signature and ExpectedTarget checks remain required.

## Configured full bundle (separate, gated production action)

The ordinary assembler exposes `bundle --production --gui-resources`, using
the **same** Day configuration adapter as `day_build_inputs.py --production`.
It is mutually exclusive with `--unsigned-day`. It does not
select Day implicitly: keep `--gui-resources` explicit. Development and GPUI
defaults are unchanged. No workflow enables production automatically.

### Environment names and compatibility

Use these canonical public inputs for Day:

| Canonical name | Compatibility alias |
| --- | --- |
| `PILOT_SIGNING_POLICY` | `PILOT_NEXT_SIGNING_POLICY` |
| `PILOT_UPDATER_PUBLIC_KEY` | `PILOT_NEXT_UPDATER_PUBLIC_KEY` |
| `PILOT_UPDATER_REPOSITORY` | `PILOT_NEXT_UPDATER_REPOSITORY` |
| `PILOT_UPDATER_BUILD` | `PILOT_NEXT_UPDATER_BUILD` |

For each field, the canonical name wins **when present**, including an empty
value. The alias is read only when the canonical name is absent. Empty or
invalid selected values fail the existing validation; they never fall back
to another value. Names can be mixed. Values are not trimmed or normalized.
The application ID and code requirement remain fixed, derived native identities,
not environment overrides. The validated tuple is translated to the shared
updater crate's legacy compile-time names inside the isolated Day build.
Ambient trust inputs and secrets are not forwarded. Receipts still must match
the exact source, recipe and compiled tuple.

This adapter applies to Day input compilation and production assembly with
`--gui-resources`. Without that flag, the GPUI parser and behavior are unchanged.
Repository/GitHub secrets, fnox entries, credentials, storage/profile names and
bundle identities are unchanged. This does not rename `DAY_UPDATER_PRIVATE_KEY`
or configure signing through a new private-key environment variable.

These are commands for a separately authorized production run, **not commands
executed as task verification**. Use tools from the selected immutable source,
with the qualified installed paths above, frozen dependencies and offline Cargo
inputs already prepared (see `prepare-day-qualification.py`). Local builds use
MBX, never CI's direct-Cargo setting. Source must include the daemon handoff
change `29102eb5f20f735c208300769f65cd9227279986` and this CLI change. Capture one
full commit once; do not resolve a moving branch again between steps.

```sh
set -euo pipefail
: "${SOURCE:?Set the full immutable post-handoff/CLI commit}"
: "${BUILD:?Set the explicit numeric target build}"
[[ "$SOURCE" =~ ^[0-9a-f]{40}$ ]]
git merge-base --is-ancestor 29102eb5f20f735c208300769f65cd9227279986 "$SOURCE"
export NSH_DAY_CARGO_MODE=mbx
export PILOT_SIGNING_POLICY=private-adhoc
export PILOT_UPDATER_PUBLIC_KEY='MbGhgDgZuJPyC81SSCJ8IVEyLks66acK5s9NKIudSsE='
export PILOT_UPDATER_REPOSITORY=babariviere/pilot
export PILOT_UPDATER_BUILD="$BUILD"
work=$(mktemp -d "${TMPDIR:-/tmp}/day-full.XXXXXX")
python3 apps/desktop/scripts/bundle_runtime.py runtime --source "$SOURCE" --output "$work/runtime"
python3 apps/desktop/scripts/bundle_runtime.py native --gui day --source "$SOURCE" --output "$work/native"
python3 apps/desktop/scripts/day_build_inputs.py --production --source "$SOURCE" --output "$work/inputs"
mkdir "$work/app"
python3 apps/desktop/scripts/bundle_runtime.py bundle --production \
  --source "$SOURCE" --bundle-build "$BUILD" \
  --runtime "$work/runtime" --native "$work/native" --executables "$work/inputs" \
  --gui-resources "$work/inputs/nsh" --output "$work/app/Pilot.app"
python3 apps/desktop/scripts/bundle_runtime.py verify "$work/app/Pilot.app"
codesign --verify --deep --strict \
  '-R=identifier "com.babariviere.pilot-next"' "$work/app/Pilot.app"
```

Assembly checks matching production/release receipts, app/helper trust/build,
runtime source/version/Node, native helpers, visual/artifact helpers, NSH release
and resource inventory before sealing. Shipping limits remain 256 MiB per file
and 2 GiB total. It refuses missing or changed inputs, not fixture-fallback.
`day_qualification.py` is deliberately **not** used for configured inputs: it
qualifies only unsigned development evidence. `candidate.py` is deliberately
**not** used: its connected app omits the runtime/helpers.

This implements a source-ready producer command. No configured full bundle,
signature, archive or installation has been produced/qualified by this change.
Keep the temporary output only for the authorized run, or remove your own
staging after consumers finish. Never install from unsigned CI evidence.

### Official update manifest prerequisites (still gated)

A code seal alone is not an official update distribution. Current source does
not supply `Contents/Resources/nsh/assets/nsh-updater.json`; the ordinary
`nsh build` input recipe does not inject an updater configuration. Automatic
update qualification additionally needs that asset bound into the **input**
resource inventory before assembly, with the same ID/key/repository and the
runtime package version, not Day's development `0.1.0`. Do not edit the assembled
bundle or its input receipt to add it. This missing update-resource wiring is
separate from the installer full-runtime producer seam.

For a later authorized official distribution, use upstream NSH 0.5.0
`update-manifest`, not `gui-release-manifest.mjs`'s legacy envelope. Prerequisites:
a prepared `RELEASE_ENTRY/nsh.json` matching the actual sealed app ID/version
and updater source/key; an existing matching Day key in NSH's base64 32-byte
seed format (`NSH_SECRET`, mode 0600); the same existing PEM via fnox; a genuine
verified archive; and an approved HTTPS `BASE_URL`. PEM and NSH seed are
different encodings of the **same** key, not permission to generate another.
No key conversion/provisioning is performed here. Upstream's command verifies
the supplied seed against `updater.publicKey`.

Once those prerequisites are met, these direct steps create the official
manifest and its required signed Pilot source/build extension:

```sh
# VERSION must equal the sealed runtime/Info.plist short version.
ditto -c -k --norsrc --noextattr --noqtn --keepParent \
  "$work/app/Pilot.app" "$work/Pilot-$VERSION-macos-aarch64.zip"
"$NSH_DAY_CLI" update-manifest --entry "$RELEASE_ENTRY" --key "$NSH_SECRET" \
  --base-url "$BASE_URL" --out "$work/official" "$work/Pilot-$VERSION-macos-aarch64.zip"
jq --arg source "$SOURCE" --arg build "$BUILD" \
  '. + {pilot: {source: $source, build: $build}}' \
  "$work/official/latest.json" > "$work/official/extended.json"
mv "$work/official/extended.json" "$work/official/latest.json"
# NSH signs the context prefix plus exact manifest bytes, not a legacy envelope.
# Keep tracing off. No plaintext key is printed or stored with distributable files.
umask 077
fnox --no-daemon --non-interactive -c apps/day/fnox.toml get DAY_UPDATER_PRIVATE_KEY > "$work/day-key.pem"
openssl pkey -in "$work/day-key.pem" -pubout -outform DER -out "$work/day-public.der"
test "$(tail -c 32 "$work/day-public.der" | openssl base64 -A)" = "$PILOT_UPDATER_PUBLIC_KEY"
{ printf 'nsh-updater-manifest\0'; cat "$work/official/latest.json"; } > "$work/framed-manifest"
openssl pkeyutl -sign -rawin -inkey "$work/day-key.pem" \
  -in "$work/framed-manifest" -out "$work/manifest.sig"
openssl pkeyutl -verify -rawin -pubin -keyform DER -inkey "$work/day-public.der" \
  -in "$work/framed-manifest" -sigfile "$work/manifest.sig"
openssl base64 -A -in "$work/manifest.sig" > "$work/official/latest.json.sig"
rm "$work/day-key.pem" "$work/day-public.der" "$work/framed-manifest" "$work/manifest.sig"
```

The extension must be added **before the final signature**. `OfficialRoot`
checks those exact signed bytes, archive hash/size, sealed app, source and build.
Normal updates need matching genuine target **and actual running rollback**
distributions; a new Day key cannot authenticate old GPUI metadata. Semver must
increase as well as the numeric build. These commands do not upload, publish,
install, hand off a daemon or prove update acceptance. No signing command above
was run. See [daemon handoff](day-daemon-handoff.md) for the separate installer
entry and [global updates](day-global-updates.md) for runtime acceptance gates.

Manifest format/signature references: upstream [CLI producer](https://github.com/longbridge/nsh/blob/f4d68f7f9f31eb7b3ecc8a4cbc31096d5c6238a1/crates/nsh-cli/src/updater.rs)
and [signature framing](https://github.com/longbridge/nsh/blob/f4d68f7f9f31eb7b3ecc8a4cbc31096d5c6238a1/crates/nsh-updater/src/lib.rs).

## Connected launch

The production bootstrap requires a verified, code-sealed native bundle.
Unsigned build inputs and `nsh run Connected.tsx` are not connected launch
substitutes. The [connected candidate recipe](day-connected-candidate.md) makes
that minimal bundle without requiring a second bundled daemon. It is not an
update/release distribution. Preserve the shipping app and use a separate
candidate directory, with the required `Pilot.app` bundle name. This Day-only
name is selected before assembly and sealing; GPUI and historical inputs keep
their original names. Bundle, service, profile and credential IDs are unchanged.

```sh
"$candidate/Pilot.app/Contents/MacOS/pilot-desktop" \
  --profile "$profile" --port "$port" \
  --daemon-id "$daemon_id" --lineage-id "$lineage_id" \
  --journal "$candidate/window-journal"
```

Every value is an explicit native selection, not a TSX field or credential.
Keep the same journal for close/reopen. The dashboard starts on All projects;
its header filter is saved with this window's drafts. Filtering reads only and
never selects New's project or retargets work. New starts with no project chosen;
a saved draft keeps its explicit project choice.

Legacy project-bound launches may still supply the complete `--project-id` and
`--project-path` pair, with optional `--planning-model` for their existing mission
enrollment path. Profile-only dashboards currently show cross-project sections
read only; project-specific mission enrollment still needs that legacy binding.
Standalone chat creation uses New's explicit project and current access instead.
No model or project is inferred just to open the dashboard.
New, final interview submission and
Start retain their separate confirmation, permission and durable-operation gates.
Successor/update launch does not infer a new planning model.

Bootstrap verifies the native code seal on a joined worker before loading
trusted bytecode. The native verifier refuses AppKit's main thread. It never
falls back to mocks or a weaker signature check.

The selected existing daemon's exact daemon/lineage and base protocol must match.
Each project's dashboard requires `dayOverview: 1` and its current project/path
and access checks. Mission controls, planning, intake and
verification also require their existing versioned contracts. A daemon without
these capabilities is unavailable, not an empty Today. Do not start a second
daemon or bypass that check. A compatible daemon update requires separate
authorization and the existing verified runtime, checkpoint/drain, signed
reservation, exact-owner exit and new-boot handoff. See
[Daemon upgrades](../../apps/desktop/docs/daemon-upgrades.md). A pause ACK is
not a drain proof, and an uncertain handoff cannot be retried.

The mock test fixtures' incoming rows are examples with no Start actions. The
connected `Incoming.tsx` route uses `LiveIncoming` and `NewControls`: opening
a new Slack or Linear request offers Start work, Later and Discard. Start
then confirms one Build chat and its exact destination. Merely viewing those
controls sends nothing; testing a real Start needs execution approval.

## Supported lanes and evidence limits

The implemented input lane is **native macOS arm64 only**, targeting macOS
15.0 or later. macOS x86_64, universal binaries and cross compilation are
unsupported. Linux x86_64/arm64, Windows, iOS, Android, Web and TUI have no
Day production input recipe here. Their existing updater/platform policies
must not be treated as Day package qualification.

Portable tests use private synthetic tools/resources and test fail-closed
recipe, artifact, receipt and resource rules. They do not execute fixture
bytecode or admit fixture signatures. Native checks are hidden build-only
evidence, not visible UI, installed-payload, signing or release acceptance.
Production signed payloads and joined automatic-update acceptance remain
unavailable until separately supplied and qualified.

See [CI and release preparation](day-ci-packaging.md) for the dormant native
qualification lane, automatic portable checks and unchanged shipping selection.
